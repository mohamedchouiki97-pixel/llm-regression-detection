# Model Regression Detection System

## What this project is
A CI pipeline that tests an LLM feature against a labeled golden dataset whenever a prompt or model changes. It scores outputs, compares them to a baseline run, detects regressions, alerts Slack, and blocks PRs with critical regressions.

The LLM feature under test is a customer support email classifier. It is intentionally simple. The product is the evaluation machinery around it.

## Phase 1: The feature under test
Goal: a classifier whose prompt is a parameter, with structured, validated output.

Build:
- `Category` enum: billing, technical, account, general
- `ClassificationResult`: category + one sentence summary
- `PromptConfig`: version id, created_at, model, system_prompt, few_shot_examples
- `classify_email(email_text, config)` using OpenAI structured outputs, temperature 0
- Return the result plus metadata: latency_ms, input_tokens, output_tokens
- Prompt files in `prompts/` (start with `v1.yaml`), loaded and validated into `PromptConfig`

Done when:
- A CLI command classifies a sample email with a chosen prompt version and prints result + metadata
- Invalid prompt YAML fails with a clear error

## Phase 2: Golden dataset infrastructure
Goal: a schema, a validator, and a reviewed dataset.

Build:
- `GoldenCase` schema: id (stable, e.g. `gc-001`), email, expected_category, ideal_summary, difficulty (easy, medium, hard), split (dev or test), tags (e.g. ambiguous, typo, short, mixed_language, sarcasm, synthetic), notes
- Dataset file has a top-level version and changelog
- Validation command: checks schema, unique ids, category balance, and prints a coverage table by category and difficulty
- Seed file with 3 example cases only, clearly marked as placeholders
- A labeling guide (`data/LABELING.md`) that defines each category and records decided gray areas
- A mechanical dev/test split: within each (category, difficulty) group sorted by id, every third case is test

Done when:
- Validator passes on a valid file and gives useful errors on a broken one
- The dataset holds 100 cases, including deliberate edge cases. They were generated by Claude, triaged by a second Claude review, then reviewed and corrected by a human against the labeling guide. Every case carries a `synthetic` tag.

## Phase 3: Eval engine
Goal: run every case, score on several dimensions, store everything.

Build:
- Async runner with a concurrency limit and retries with backoff; an empty API balance stops the run
- Cache LLM responses keyed by a hash of the full prompt content, the model, and the email (and, for the judge, its model, version, and inputs) so reruns are cheap during development; cache can be disabled
- Scoring per case:
  - category_match (binary)
  - summary_score 1 to 5 from an LLM judge with a written rubric, returning score + short reasoning as structured output
  - latency_ms, tokens, estimated cost
- A case "passes" if category matches and summary_score >= a configurable threshold
- API errors are recorded per case, not counted as failing answers
- Store each run in SQLite: run metadata (run id, prompt version, model, judge model and version, dataset version, git sha, timestamp) and per-case results

Done when:
- One command runs the full dataset and stores a run
- Unit tests cover scoring logic with fake LLM outputs

## Phase 4: Comparison and statistics
Goal: the core value. Diff a run against a baseline and decide if it is a real regression.

Build:
- Compare run vs baseline (default: latest clean, comparable run on main; in CI the PR job rebuilds the baseline by running the base branch's prompt): overall pass rate delta, per-category, per-difficulty, and per-split deltas, regressions (pass to fail), improvements (fail to pass)
- Configurable thresholds: warning and critical deltas (start at 3 and 8 percentage points)
- McNemar exact test on flipped cases to report whether the change is statistically meaningful; report the p value alongside the threshold result
- Slow drift: 7-run moving average of pass rate; warn if it falls below a configurable floor even when no single run alerted
- Error rate: errored cases are left out of every delta and the test; too many errors fail the run as "eval incomplete", and error-heavy runs are never used as baselines
- Final status: pass, warn, or fail

Done when:
- Unit tests cover diffing, thresholds, McNemar, and drift with hand-built fake runs
- Measure judge noise: run the same prompt three times and report how many cases flip; document it

## Phase 5: Reporting and alerts
Build:
- HTML report: run metadata, scorecard vs baseline, regressed cases with old vs new output side by side (including judge reasoning), trend chart of the last N runs (inline SVG, so the report works offline)
- Slack message via webhook: status, headline numbers, link to report. Skip gracefully if no webhook is set.

Done when:
- Changing a prompt to something deliberately worse produces a report that clearly shows the regressed cases

## Phase 6: CI/CD and Docker
Build:
- GitHub Action on every PR; it runs the eval only when the PR touches `prompts/`, `data/`, or the workflow, and otherwise skips so the required check still reports
- Runs eval, uploads HTML report as an artifact, posts a PR comment with status and headline numbers, fails the check on critical regressions
- A main branch workflow that runs the eval after prompt or data changes and keeps run history for drift and the trend chart
- A tests workflow that runs pytest and builds the Docker image
- Dockerfile packaging the runner, dataset, and report layer; config via env vars (OPENAI_API_KEY, SLACK_WEBHOOK_URL, thresholds)

Done when:
- A PR with a bad prompt change is blocked, and a good one passes
